## 1. 仓库与分支（Mock）

- **主分支**：`main`，仅通过 **Pull Request** 合并，需 **1 名** Reviewer 批准（训练营可降为同学互审）。
- **功能分支**：`feature/<模块简称>-<需求键>-<简述>`，例：`feature/m1-req-msg-search`。
- **修复分支**：`fix/<简述>`。
- **禁止**：直接向 `main` 强推；携带密钥、`.env` 真实值入库。

## 2. 提交与 PR（Mock）

- **Conventional Commits** 建议：`feat:`、`fix:`、`docs:`、`chore:`、`refactor:`。
- **PR 描述**须含：关联 Spec 文档路径、自测说明、截图（前端）或 curl 示例（API）。
- **Squash merge** 为默认（可按班级调整）。

## 3. 代码规范（Mock）

| 层级 | 约定 |
|------|------|
| 前端 | ESLint + Prettier；函数组件；目录 `src/features/<域>/` |
| 后端 | Black + Ruff（或 flake8）；Blueprint 按域拆分；类型注解建议 |
| API | `camelCase` JSON 与总表 OpenAPI 一致；错误体统一 |

## 4. 机密与配置（Mock）

- 密钥仅存 **GitHub Actions Secrets** 或本地 `.env`（`.gitignore`）。
- 对象存储、RDS 连接串 **禁止** 写入 Spec 正文，用占位符 `{{ENV}}`。

## 5. 文档与需求（Mock）

- 需求 ID：`REQ-<模块>-###`；用户故事：`US-<模块>-###`。
- 变更先改 **本模块 Spec**，再改代码；重大契约变更同步 **09** 与集成方模块。

## 6. 阿里云使用纪律（Mock）

- 生产与开发 **账号/资源组** 分离；公网入口最小暴露。
- 日志脱敏字段清单见各模块 `07-非功能需求与约束.md`。
- **各模块建议使用的云产品与 CoPaw 依赖**（ECS、RDS、OSS、SLS、API 网关、百炼/灵积 Key 等）见 **`00-阿里云资源与CoPaw清单.md`**。

## 7. CoPaw 使用原则（全项目 · 宜用与勿强行）

**目标**：在 Workshop/本仓库范围内 **适度** 使用 CoPaw 作为 **运行时扩展与编排层**，与 **Flask BFF + React** 主链路并存；**不把** 业务真源与合规规则塞进 CoPaw 内核。

### 7.1 总体策略（浅集成）

| 原则 | 说明 |
|------|------|
| **BFF / 模块 API 为契约真源** | 各模块 `09` 定义的 REST 行为 **必须** 可由纯 Flask + DB **独立验收**；CoPaw 通过 **HTTP 调用** 同一套 API，而非替代实现。 |
| **CoPaw 做「胶水」** | Skills、Channel、Cron、MCP、多 Agent 等用于：定时拉数、封装外部工具、推送出站、探索式对话入口、可选的多角色编排。 |
| **禁止** | 为「用上 CoPaw」而把 **简单 CRUD、分页列表、鉴权中间件** 搬进 Agent 循环；在 CoPaw 内复制一套与 `09` 不一致的私有 API（除非明确标为 PoC 且不入主链路）。 |

### 7.2 宜用 CoPaw 的典型场景（与能力模块对照）

| CoPaw 能力（概念） | 宜用场景 | 五模块落点（参考） |
|--------------------|----------|-------------------|
| **Skills** | 脚本化调用 `POST/GET …/api/v1/...`、拼装提示上下文、教师演示「一句话触发流水线」 | 全模块可选；**M2** 触发同步、**M3** 触发解析检查、**M5** 辅助发起辩论会话 |
| **MCP / 工具** | 封装 Wind/新浪等 **合规可替换** Provider，返回结构化结果供 BFF 落 `tool_trace` | **M2**、**M5** 只读行情/检索（与各自白名单一致） |
| **Cron** | 定时拉取、对账、重试失败批次 | **M2** 调度旁路、**M4** 轮询补充 |
| **Channel** | 钉钉/飞书等 **出站**（文案仍经 BFF 合规与审计） | **M4** 主推 |
| **多 Agent / 协作** | 多角色对话、与 `11` 编排策略一致 | **M5** 首选；可选「BFF 内编排」与「CoPaw 多 Agent」二选一，**须在 `11` 冻结** |
| **Console 外链** | 从 CoPaw 管理台跳到「投研工作台」SPA | 横切 UX，**不**替代业务路由 |

### 7.3 不宜强制使用 CoPaw 的场景

- **M1 类纯读模型**：消息列表、搜索、已读状态 — **Flask + PG 为主**；CoPaw 仅可做「摘要收件箱」类 **可选** Skill，**不得** 作为唯一读路径。  
- **数据库迁移、CI、单元测试、纯前端路由与表单校验** — 使用常规工具链。  
- **合规规则单一真源** — 仍以 BFF/配置仓库为准（与 `docs-ira` 方案一致）；CoPaw 侧 **调用** 扫描接口，**不** 分叉维护规则集。  
- **高 QPS 同步读** — 不走 LLM/Agent 绕路；必要时直连 BFF 或缓存。

### 7.4 验收与文档

- 模块 `08-系统架构与技术选型.md` 中建议增加 **「CoPaw 边界」** 小节（一两段即可）：写明本模块 **哪些能力走 CoPaw、哪些永不走**。  
- PR 评审：若引入新 Skill/Channel，须注明 **调用的 `09` 路径** 与 **失败降级**（CoPaw 不可用时 BFF 仍可演示）。
